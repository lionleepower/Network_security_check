# 浏览器 WebRTC 与 Claude Code 的联网路径

## 检测结果如何归因

DNS、HTTPS 出口与 WebRTC／STUN 分别验证，不能相互替代。先看检测明细，再看页面总评：总评“未泄漏”与明细“国内公网地址暴露”可能矛盾；无候选也可能是服务器不可达，不能直接判定保护成功。

WebRTC 返回的公网地址可与当前宽带出口、对应 STUN 连接的 Clash 规则链对照。浏览器安全 DNS 与 53 端口劫持不会自动限制任意 STUN UDP。国内 STUN 因国内分流走 DIRECT 时，海外 HTTPS 出口正常也可能同时暴露宽带地址；不能为此未经授权代理全部国内流量或封禁所有 UDP。

浏览器看到海外 IPv6 不能单独证明本机 IPv6 偷跑。用公开 HTTPS trace、指定本机代理的同目标请求，以及本机地址／路由区分远端出口与本机绕过。节点名称或普通查 IP 的国家不能代表 Claude 目标的出口；机场可能按目标另行路由。以目标实测为准，不向未授权第三方上传连接或完整日志。

## 按站点限制与专用浏览器

仅需保护特定网站时，先核对该浏览器版本是否支持按来源设置 WebRTC IP handling，以及登录配置文件、嵌入来源和策略适用性。Edge 的 `WebRtcIPHandlingUrl` 可指定 `disable_non_proxied_udp`，但官方列有个人 Microsoft 账号配置文件适用性限制。策略状态 OK 或注册表值正确都不是行为验证；测试仍泄漏时不宣称已生效，也不把失败原因猜成定论。

工具拒绝内部页面时遵守限制，不能换工具访问同一被禁页面。可请用户手动检查策略状态，再用允许的 HTTPS 检测页面验证行为。若临时加入检测站 URL，验证后移除；撤回失败实验时只恢复本次值，避免覆盖后来修改或删除其他策略。不要因一次策略失败就升级成全浏览器或系统级限制。

用户接受专用浏览器及重新登录时，可以创建独立数据目录作为范围明确的替代方案：

- 先发现实际浏览器路径、宿主用户目录和 Clash 代理端口。沙箱中的 LOCALAPPDATA 等变量可能被重定向，不能据此把宿主浏览器数据写到沙箱临时目录。
- 新数据目录放本机私有应用位置，不能放项目／Git／技能目录；检查目标不存在，拒绝覆盖或复制原 profile 的 Cookie、密码、扩展与账号。不要在正在运行的 profile 上直接改 Preferences。
- Chromium 系浏览器可按版本核对，在新 profile 首次初始化 `webrtc.ip_handling_policy=disable_non_proxied_udp`，并设置现有回环 HTTP 代理。此项是候选配置，仍需在实际产品版本验证，不能把 Chromium 源码等同于所有衍生浏览器保证。
- 专用快捷方式携带 `--user-data-dir`、正确的 profile 与 `--proxy-server=http://<本机回环地址>:<已发现端口>`。是否补充 QUIC 限制、代理绕过列表等按目标决定，不关闭 TLS 验证或浏览器安全功能。不要只依赖未经证实的强制 WebRTC 命令行开关。
- 限制覆盖专用实例内的网站，不自动覆盖原浏览器、桌面 Claude 或 CLI。显式连接 Clash 仍遵循其规则，不等于全部请求强制走 AI 组，也不构成系统 kill switch。实时音视频可能受影响。
- 由用户重新登录；在同一专用实例用已获授权的检测站验证。窗口名称或设置文件只能证明确实建立配置，不能代替行为复测。区分“工具独立复测通过”“用户反馈正常”和“尚未验证”。

交付桌面入口、启动顺序（先 Clash，后专用入口）、数据目录和恢复方式。普通浏览器的链接不会自动转到专用实例。退出后仍保留登录数据；停用可关闭专用窗口，未经授权不删除会话目录。不要让用户日常重复运行初始化脚本。网络、代理端口、入口参数或浏览器大版本变化后按需复测，无需每天检测。

## 先辨认 Claude Code 的入口

用户说 Claude Code 时，区分终端 CLI、编辑器扩展、Claude 桌面应用 Code 页面及云端／SSH／WSL 会话。PATH 找不到 `claude` 不能判未安装：桌面应用可能自带 Code 核心。优先只读发现；无法确定时询问日常入口，不擅自安装 CLI。

Windows 桌面版的发现要点：

- 用 `Get-AppxPackage` 按 Claude／Anthropic 筛选包名、版本、安装位置；也核对普通安装登记。Microsoft Store 版数据可能位于包的 `LocalCache\Roaming\Claude`，不能只查普通 APPDATA。包名、版本及用户路径从本机发现，不硬编码本次会话值。
- 查看相关配置的允许键、内置 `claude-code` 版本目录和精确目标进程／父进程；不遍历历史会话、认证文件或全部浏览器进程。文件存在、包安装、进程运行与实际会话正在联网是不同证据。
- 检查用户 `~/.claude/settings.json` 的代理 env 键、Desktop 对应环境配置，以及用户／机器级代理变量。只输出是否设置、协议、回环属性、端口等脱敏摘要；运行检查 shell 的环境不能代表已启动 Desktop／Code 子进程的环境。
- `wsl --list --verbose` 可先盘点；发行版已停止时不为排查擅自启动。Code 页面还能选择本地、云端、SSH 或 WSL，安装了 VM／WSL 组件不证明当前会话使用它。

## Claude 代理候选与验证边界

先检查 TUN 和现有规则；没有显式代理变量不等于直连泄漏。用户只要求检查或选择暂不修改时，到此记录结论与缺口，保持环境不变。

获准配置后，依据官方当前版本选择 HTTP／HTTPS 代理变量；Claude Code 官方不支持直接配置 SOCKS 代理。目标是 HTTPS 服务也可使用 `HTTPS_PROXY=http://<回环地址>:<端口>`，它表示到本机代理的协议，不应误写成不受支持的 TLS 代理入口。避免 `NO_PROXY=*` 或包含需保护的业务域名；检查小写变量与已有值的优先级，不盲目覆盖。

用户级 `~/.claude/settings.json` 的 `env` 是候选持久入口，保留其他字段并备份。桌面应用管理连接的会话可能限制项目级配置的生效范围；查官方规则而不是把项目 settings、全局环境和 Desktop 设置视为等价。变更是否需要重新启动／新建会话也按实际版本和授权确定。

分层验证，不把检测范围扩大成结论：

1. 通过现有代理、不携带凭据访问公开 HTTPS 端点，验证 TCP、CONNECT、TLS、HTTP。根路径 404 可证明收到 HTTP 响应，不证明账号、模型 API 或 Code 会话可用；不为网络测活默认调用付费模型。
2. 对照官方域名清单和实际连接检查登录、API、资源、MCP 内容与预览端点的规则顺序。仅一个后缀缺少专用规则不证明已直连，还需核对后续匹配；不代理整个共享 CDN 来补单个服务。
3. 观察实际 Code 会话的进程、目标和 Clash 规则链；`/status` 等只用于当前产品确实支持的界面。应用未运行、没有会话或观察窗口没有连接时，写明尚未验证，不能以“无连接”判网络故障或安全。
4. Code 调用的 MCP、子进程、开发服务器和浏览器工具可能独立联网；主 API 代理变量不保证覆盖它们。云端／远端会话从执行端联网，不能假设会使用本机回环代理；WSL 继续参考 verification.md。

交付说明 AI 组的当前实际选择与回退状态。读到手动节点时如实说明未启用自动组，未获修改授权不替用户切换。所有地区与 IP 都只是采样时刻、采样目标的结果。
